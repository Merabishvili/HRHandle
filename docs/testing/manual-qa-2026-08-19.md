## 3. Authorization / Login

**Result:** 🔴 fix-during — one bug (public vacancy URL).

- Logged in with "remember me" checked → session persisted, dashboard opened. 🟢
- **BUG:** The **public vacancy URL** (org `public_page_slug`) is **not filled** — it renders as
  just a single `-` character.

**Root cause:** `slugify()` in [`lib/onboarding.ts`](../../lib/onboarding.ts) does
`.replace(/[^a-z0-9\s-]/g, '')`, which strips **all** non-Latin characters. A Georgian/Russian
company name (e.g. `კომპანია`) collapses to `''` or, if it had a space, to a lone `-`. The slug
should be **transliterated** Georgian/Russian → Latin before slugifying, so the org name still
produces a usable public URL. See fix plan → *Fix B*.

## 🔴 Google + Microsoft OAuth — `redirect_uri_mismatch` (code bug — FIXED)

Both **Google Calendar** and **Microsoft Teams** "Connect" failed with a redirect-URI
mismatch on production. Both builders derive the redirect URI from the **same**
`NEXT_PUBLIC_SITE_URL`, so two providers failing identically pointed to a shared cause,
not two registration gaps.

**Root cause:** [`lib/google/calendar.ts`](../../lib/google/calendar.ts) and
[`lib/microsoft/graph.ts`](../../lib/microsoft/graph.ts) did **not** strip a trailing slash
from `NEXT_PUBLIC_SITE_URL` (unlike [`billing.ts`](../../lib/actions/billing.ts) +
[`calendly.ts`](../../lib/actions/calendly.ts), which already do). A prod value like
`https://hrhandle.com/` yields `https://hrhandle.com//api/auth/.../callback` (double
slash) → rejected by both Google and Azure.

**Fix (code):** new shared [`lib/site-url.ts`](../../lib/site-url.ts) `siteBaseUrl()` strips
trailing slash(es); both OAuth redirect builders now use it. Tested in
[`lib/__tests__/site-url.test.ts`](../../lib/__tests__/site-url.test.ts).

**Still verify after deploy** (in case the prod value isn't a trailing slash but `www.`/
`http`/wrong host): production `NEXT_PUBLIC_SITE_URL` should be exactly `https://hrhandle.com`,
and `GOOGLE_CLIENT_ID` / the Azure `client_id` must match the app where the redirect URIs
are registered. Requires a **redeploy** for the code fix to take effect.

### Update — redirect_uri resolved; now two time-based expiries (both CONFIG, not code)

Retested: both flows now get **past** the redirect_uri step. New errors, both explained by
"expired on their own" (matches "worked before, didn't change anything"):

- **Google → `Error 403: access_denied`** — "hrhandle.com has not completed the Google
  verification process… only developer-approved testers." The OAuth **consent screen is in
  "Testing" publishing status**; only listed test users can authorize, and Testing-mode
  refresh tokens also expire after **7 days**.
  **Fix (Google Cloud Console → APIs & Services → OAuth consent screen):** add the tester
  email(s) under **Test users** (fastest), or **Publish app** to production (the sensitive
  `calendar.events` scope may then require Google verification).
- **Microsoft → `token_exchange_failed`** (`msConnect.tokenFailed`) — authorize succeeded,
  the token exchange failed. Almost certainly an **expired Azure client secret** (secrets
  have expiry dates; a lapse breaks token exchange with no config change — AADSTS7000215/222).
  **Fix (Azure Portal → App registrations → app `d7ef9a54-…` → Certificates & secrets):**
  check the secret's expiry; if expired, create a new one and update `MICROSOFT_CLIENT_SECRET`
  on Vercel (prod), then redeploy. Confirm via Vercel logs: `[microsoft/graph] exchangeMicrosoftCode failed …`
  prints the exact `AADSTS…` code (secret vs redirect). Also confirm the redirect URI is
  registered under the **Web** platform on the Authentication tab.

### ✅ RESOLVED (2026-08-19) — both integrations connect

Definitive root causes from the logs / screens, both **config on the operator side** (no app
code fix needed beyond the trailing-slash hardening already shipped):

- **Microsoft** — `AADSTS7000215: Invalid client secret provided … is the client secret VALUE,
  not the client secret ID`. `MICROSOFT_CLIENT_SECRET` on Vercel held the secret **ID** (a GUID)
  instead of the one-time secret **Value**. Fix: new secret → copy the **Value** column → set on
  Vercel (prod) → redeploy. App ID + redirect URI were already correct. **Connected.**
- **Google** — after publishing, the "Google hasn't verified this app" screen for the sensitive
  `calendar.events` scope. **Not a block** — testers proceed via **Advanced → Continue**. Full
  Google verification (needs the Search Console domain-ownership TXT, added to Spaceship `@`) is
  only required to remove the warning for the public; deferred to launch. **Connected.**

**Two gotchas worth remembering (candidates for docs):** Azure **secret Value ≠ Secret ID**;
Google sensitive-scope testers use **Advanced → Continue**.
