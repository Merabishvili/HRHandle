**Result:** 🔴 fix-during — one bug.

## 3. Authorization / Login

**Result:** 🔴 fix-during — one bug (public vacancy URL).

- Logged in with "remember me" checked → session persisted, dashboard opened. 🟢
- **BUG:** The **public vacancy URL** (org `public_page_slug`) is **not filled** — it renders as
  just a single `-` character.

**Root cause:** `slugify()` in [`lib/onboarding.ts`](../../lib/onboarding.ts) does
`.replace(/[^a-z0-9\s-]/g, '')`, which strips **all** non-Latin characters. A Georgian/Russian
company name (e.g. `კომპანია`) collapses to `''` or, if it had a space, to a lone `-`. The slug
should be **transliterated** Georgian/Russian → Latin before slugifying, so the org name still
produces a usable public URL. See fix plan → *Fix B*.

## 4. Registration via Google (2026-08-19)

**Result:** 🟢 signup OK; 🔴 one fix-during (email defaults) + 🟡 one design item (calendar).

- Google OAuth sign-up worked; landed in dashboard. 🟢
- 🔴 **Default candidate-email templates showed in English despite a Georgian org.**
  Root cause: `runOnboarding` never seeded `organizations.default_content_locale`,
  so every org defaulted to `en`. Candidate emails resolve on **org content locale**
  (separate from the recruiter's UI locale by design), so defaults rendered English.
  The KA/RU default copy already exists in [`emails.source.json`](../../messages/emails.source.json).
  **Fixed:** onboarding now seeds the org content locale from the signup language —
  email signups from `user_metadata.locale`, OAuth from the onboarding `NEXT_LOCALE`
  cookie ([`lib/onboarding.ts`](../../lib/onboarding.ts), [`lib/actions/onboarding.ts`](../../lib/actions/onboarding.ts)).
  The "customized template linked to the org, no default afterwards" behavior was
  already correct (`saveEmailTemplate` + `resolveTemplate`). Existing prod test orgs
  (3) backfilled `en → ka`.
- 🟡 **Google Calendar not auto-linked after Google signup.** Decision: **post-signup
  prompt** (not forced calendar scope at signup). The Calendar integration is a
  separate OAuth (`/api/auth/google/callback`) storing tokens in the org integration;
  Google sign-in doesn't capture them. **Planned follow-up**, not yet built: a
  "Connect Google Calendar" prompt/banner after onboarding.

## Post-signup "Connect integrations" prompt — BUILT (2026-08-19)

Replaces the two 🟡 auto-link items above (decision: post-signup prompt, not forced
scopes at signup). A dismissible dashboard banner nudges OAuth users to connect the
integration matching their sign-in provider, until they connect or dismiss it.

- Decision logic (pure, tested): [`lib/integrations/prompt.ts`](../../lib/integrations/prompt.ts)
  — Google signup → Google Calendar/Meet; `azure` signup → Microsoft Teams/Outlook;
  email signups / already-connected / dismissed → nothing.
- Server component [`integration-connect-prompt.tsx`](../../components/integrations/integration-connect-prompt.tsx)
  short-circuits before any DB query (only OAuth + not-dismissed users incur the
  token lookup); rendered from the dashboard layout above page content.
- Client banner [`integration-connect-banner.tsx`](../../components/integrations/integration-connect-banner.tsx) —
  links to the existing `/api/auth/{google,microsoft}` connect flow; dismissal stored
  in the `int_prompt_dismissed` cookie (server-readable, no flash).
- i18n: `integrations.prompt*` keys (en/ka/ru). Tests: [`lib/integrations/__tests__/prompt.test.ts`](../../lib/integrations/__tests__/prompt.test.ts).
- Docs: [google.md](../../4-integrations/google.md), [microsoft.md](../../4-integrations/microsoft.md).
